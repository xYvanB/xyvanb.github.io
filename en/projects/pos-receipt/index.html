POS Receipt

A lightweight POS that a few associations in the village where I live use during their festivals. You build the order from the menu, print a 51 mm receipt along with the slips for the kitchen and the bar, and stock counts down on its own: the till and the kitchen always know what's still available. Flask REST API on MySQL, a frontend in a single HTML file with no framework and no build, all on the local network.

PythonFlaskMySQLVanilla JSREST API

What it does

This one wasn’t built to solve a problem: it’s simply the program a few associations in the village where I live use as a cash register and stock room during their festivals. At the till you take the order, print the receipt and move on; the kitchen cares about one thing only, knowing in real time how many portions of each dish are left. Everything else in the program exists to hold those two things together.

The interface is split into five tabs — Orders, Warehouse, Statistics, Receipts and Settings — and runs on a PC at the till, or on a tablet in the dining area pointed at the same server.

How it works

An order’s whole round trip is this. You pick the products from the menu, set the number of covers and optionally a customer name and a note, then move to the summary: subtotal, cover charge worked out from the headcount and total, with room to fix a quantity or drop a line before confirming. On confirmation, in a single transaction the backend records the receipt and its line items and decrements the stock of every product ordered. From that moment the warehouse is up to date for everyone: anyone looking at the Warehouse tab from another device sees the same quantities.

Then there’s the printing, which is my favourite part. What comes out of the 51 mm thermal printer isn’t a single slip: the first is the customer’s receipt, with the summary and the total, followed by a separate docket for every department involved — the waiter for food, the bar for drinks, the bar for coffee. Each docket carries only its own lines, and is printed only if the order contains something in that category: a round of beers produces no docket for the kitchen. They all come out on the same strip, separated by the dashed lines you tear along, and the page is set to a fixed width with automatic height, so it comes out exactly as long as it needs to be and wastes no paper.

Every receipt stays browsable, searchable by customer name and reprintable from its own tab; if one gets deleted — a mistaken order, a customer changing their mind — the quantities go back into stock, because deletion runs the inverse operation and credits the units back.

The Warehouse tab handles products: price, stock on hand, category, creation and deletion. The order they appear in on the menu is changed by dragging them around, which sounds like a detail but matters a lot at the till: you want the popular dishes at the top, and that changes from one festival to the next. Statistics gives the summary of takings, covers and dishes sold — printable too, handy at the end of the night — with the option to reset everything before the next event. Settings holds the name, address, event date and cover charge, which is what ends up in the receipt header, along with the categories and products.

How it’s built

The backend is Python with Flask: a REST API over MySQL and a little over a dozen endpoints, with the delicate operations — creating and deleting a receipt — wrapped in a transaction, so stock levels and order lines can never drift apart. The schema is four tables plus settings, with foreign key constraints that stop you deleting a product that already appears on a receipt.

The frontend is deliberately bare: a single HTML file with the CSS and JavaScript inside it, no framework, no build step, nothing to download. You open it in a browser and it works. That choice comes from looking at where it actually runs — a borrowed laptop, under a marquee, often with no internet — and where the only thing that counts is that it starts on the night of the festival. On Windows a .bat file launches the backend, the frontend and the browser page: double-click and you’re working. Other devices point at the server’s local IP and see the same data.
